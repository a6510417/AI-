# 数据协议：布局 v2／资产内容 v1

本文是本地工具机器字段的唯一规范。人类写作方法见技能库，命令参数见[接口规范](接口规范.md)。所有JSON使用UTF-8。项目清单 `project.json.schema_version` 为布局版本：新项目为2，旧项目1继续读取；工作资产 `asset.json.schema_version` 和资产内容协议继续为1。版本号为三段数字，如 `1.0.0`。不使用注释或尾随逗号。

## 1. 项目目录与登记

项目根目录位于工作区根的 `projects/IP编号_项目名/`。布局v2按机器资产和制作文件的用途分开：

| 目录 | 用途 |
| --- | --- |
| `assets/<TYPE>/<资产ID>/` | 13类工作资产，每个目录包含原协议的 `asset.json`、正文及附件 |
| `sources/` | 输入原稿、授权与原始参考；需要版本引用的素材仍登记MEDIA |
| `production/` | 制作工作文件、审核输入及脚本 |
| `deliveries/handoff/` | 新漫改交接包 |
| `deliveries/resume/` | 新小说续作包；迁移保留的历史续作包也放此处 |
| `deliveries/export/` | 迁移保留的历史导出目录，不作为新导出的默认位置 |
| `deliveries/views/` | 根据精确REPORT版本生成的可移植派生阅读视图 |
| `.ip-system/` | 工具管理的冻结快照、审核、事务、生命周期与迁移记录 |

布局v1项目仍按登记的安全路径读取、保存和交接；下列八目录只用于v1兼容，不与v2资产目录混建。升级流程见[重构实施说明](重构实施说明.md)。

**v1兼容目录：**

| 目录 | 主要内容 |
| --- | --- |
| `00_项目管理` | 策划、计划、采用和审核说明 |
| `01_世界观资产` | 世界规则、地点与相关状态 |
| `02_人物资产` | 人物、关系、动机、知情范围、道具 |
| `03_小说资产` | 剧情规划、章节包、小说状态 |
| `04_漫剧资产` | 剧集、场次、镜头和桥接成果 |
| `05_视觉资产` | 视觉描述、提示词和实际参考素材 |
| `06_AI生成记录` | 实际生成任务记录；没有提交时不得伪造结果 |
| `07_发布资产` | 本地交接导出及将来实际发布使用的资产 |

根目录 `project.json` 的最小结构：

```json
{
  "schema_version": 2,
  "project_id": "IP003",
  "name": "新故事",
  "assets": [
    {
      "asset_id": "IP003-CH-001",
      "type": "CH",
      "path": "assets/CH/IP003-CH-001",
      "aliases": [],
      "versions": [],
      "adopted_version": null
    }
  ]
}
```

`path` 是包含 `asset.json` 的工作目录，相对当前项目根目录。资产目录不能相互包含，不能使用 `.ip-system`；绝对路径、`..`、符号链接和目录联接都被拒绝。别名 `aliases` 只用于追溯旧编号，正式依赖必须使用新 ID。

`versions`、`adopted_version` 以及项目的 `adoption_history`、`operations`、`review_items`、`review_dispositions`、`content_reviews`、`exports`、`resumes` 由工具管理，不要手工编造采用历史、校验值、审核证据或处理记录。优先通过 `new-asset` 建立骨架；外部已创建的工作目录仍可用 `save-version --path` 登记，或先按上述结构手动登记。

## 2. 资产结构与引用

每个工作资产目录必须包含 `asset.json`：

```json
{
  "schema_version": 1,
  "project_id": "IP003",
  "asset_id": "IP003-CH-001",
  "type": "CH",
  "title": "第一章",
  "version": "1.0.0",
  "source_kind": "原创创作",
  "adoption_status": "建议",
  "refs": [],
  "data": {
    "events": [
      {
        "event_id": "E01",
        "story_time": "第一日清晨",
        "summary": "主人公收到一封等待送出的信"
      }
    ]
  }
}
```

ID 格式为 `IP数字-类型-至少三位数字`；项目编号、ID 前缀、类型和登记项必须一致。支持类型：

| 类型 | 含义 | 类型 | 含义 |
| --- | --- | --- | --- |
| `WORLD` | 世界设定 | `CHAR` | 人物 |
| `LOC` | 地点资产 | `PROP` | 道具 |
| `PLOT` | 策划与剧情规划 | `STATE` | 连续性状态变化 |
| `CH` | 章节包 | `EP` | 剧集 |
| `SC` | 叙事场次 | `SHOT` | 镜头 |
| `PROMPT` | 提示词 | `MEDIA` | 媒体资产 |
| `REPORT` | 审核或制作报告 | — | — |

`source_kind` 允许值：**原文事实、梗概信息、分析推断、改编建议、用户设定、参考图观察、原创创作**。`adoption_status` 允许值：**沿用来源、已采用改编、建议、待核实、已采用原创**。它们记录内容语义，独立于工具实际采用指针；在文字中写“已采用原创”不构成 `adopt` 操作。任务进度和审核结论放在对应报告或 `data` 内容内，不给这两个字段增加“已完成”“待审核”等混合值。

统一引用对象如下，`event_id` 可选：

```json
{"asset_id": "IP003-CH-001", "version": "1.0.0", "event_id": "E01"}
```

`refs`、`data` 以及章节六份 JSON 内的引用均遵循此结构。除顶层资产或章节文件身份外，带 `asset_id` 的对象被识别为引用，必须带 `version`。工具递归收集依赖，识别到引用后仍继续检查其嵌套字段，不要求在 `refs` 重复一份嵌套引用；外层身份字段不能遮住内部的 `reference_bindings[].media` 或其他引用。禁止跨 IP、缺版本或引用不存在的历史快照；带 `event_id` 时，必须定位到该版本 CH 的实际 `data.events` 条目。

## 3. 类型最低内容

### 章节 CH

除了 `asset.json` 元数据，每章必须整体包含七个交付文件：

| 文件 | 要求 |
| --- | --- |
| `正文.md` | Markdown 正文；采用时非空 |
| `摘要.json` | 实际事件、因果与本章结果 |
| `出场人物.json` | 人物引用、登场和知情变化 |
| `场景.json` | 地点引用、小说片段和故事时段 |
| `情绪节点.json` | 事件、人物情绪与表现 |
| `新增设定.json` | 候选新增设定及审核信息；没有新增可写 `[]` |
| `漫改建议.json` | 可视化事件、保留信息与改编建议 |

六份 JSON 必须为对象或数组；具体创作内容由模板和内容审核负责。顶层若提供 `project_id`、`asset_id`、`chapter_id`、`version`，必须与所属章节一致；`chapter_id` 等于该 CH 的 `asset_id`。两个 ID 字段可以并用，但都必须正确；不要求旧文件补写原来没有的身份字段。新章节骨架默认提供 `project_id`、`chapter_id`、`version`。`场景.json` 表达小说片段，不等同于 `SC` 资产。

`data.events` 为非空数组，每项含唯一 `event_id`、非空 `story_time` 与 `summary`。七份交付文件加元数据整个目录一起保存，不能拆成各自版本。缺文件不能保存；草稿可以保留空正文及合法的空对象/数组，但不能采用。JSON 文件本身留白不符合 JSON 语法。除无新增设定可用 `[]` 外，采用时六份配套资料须有实际内容。

已有剧本也沿用 CH 来源包。`正文.md` 保留原文、分集和场次标记，不改写成小说来满足目录名称；可把原始文件作为同目录附件保留。在摘要和 `data.events` 中记录原分集／场次、原文位置及事件，可用可选的 `source_format`、`source_location` 说明来源格式和位置；七文件整理实际人物、场景、情绪、设定与改编建议后，再建立 EP、SC、SHOT 的精确事件引用。一个 CH 包可以对应一个方便追溯的来源单元，不强制等于一个成片剧集。原稿改变时保存新版本并复核下游，不改写旧来源快照。

### 剧集、场次与镜头

| 类型 | `data` 必填内容 |
| --- | --- |
| `EP` | `episode_number` 正整数；`chapter_refs` 非空 CH 引用数组 |
| `SC` | `scene_number` 正整数；`episode` 为 EP 引用；`location` 为 LOC 引用；`source_refs` 为非空 CH 事件引用数组 |
| `SHOT` | `episode` 为 EP 引用；`scene` 为 SC 引用；`source_refs` 为非空 CH 事件引用数组；`shot_number` 正整数；`start_seconds` 非负数；`duration_seconds` 正数；下表全部文字字段 |

| 镜头文字字段 | 含义 |
| --- | --- |
| `story_time` | 故事发生的时段，与播放时间分开 |
| `scene_description` | 地点、时段及场地状态 |
| `characters` | 在画人物与状态，明确区分画外人物；无则写“无” |
| `action` | 可表现的动作起点、过程与终点 |
| `emotion` | 情绪与可见表现 |
| `dialogue` | 台词、说话者及跨镜续接；无则写“无” |
| `shot_size` | 景别及必要变化 |
| `camera_movement` | 固定或明确的运动路径 |
| `lighting` | 光源与光影状态 |
| `video_prompt` | 可独立复制的单镜中文视频提示词 |
| `visual_description` | 本镜具体可见画面描述 |

镜头编号、时长和原九项文字内容共同保留原分镜十一项；新增的是归属、来源和视觉描述。SC 的来源章节必须属于其 EP；SHOT 的 EP 必须与 SC 的 EP 一致，来源事件必须包含在 SC 的来源事件内。一个 EP 可引用多个 CH，多个 EP 可引用同一 CH。

SHOT 代表一个剪辑镜头；一次视频生成任务可以覆盖多个 SHOT，但制作说明须保留镜头顺序、起止状态和各镜取用关系，不能将多镜生成任务写成一个混合镜头来绕过播放树。摄影设计 `photography`、起始状态 `entry_state`、结束状态 `exit_state`、时长依据 `duration_basis`、声音设计 `sound` 等是可选补充，可为文字或有内容的结构。中文交接在十一项之后展开所有尚未展示的字段；上述字段使用中文标签，其他字段保留原名和值。旧资产不必补写这些字段。

当前工具以当前采用 SHOT 及其引用的 SC、EP 建立播放树，历史 SHOT 作为其他资产依赖入包时不参与播放编号或时长。当前镜头不能同时混用同一 EP 或 SC 的多个版本。同一剧集内镜头起点和时长不得相互重叠。原技能支持的叠化等有重叠剪辑可以在手动方案中表达，本版工具尚未提供对应过渡字段；不要为通过检查篡改实际规划时间。

### 状态 STATE 及其他类型

`PLOT.data` 在原有策划字段之外，还必须有：

| 字段 | 要求 |
| --- | --- |
| `reading_mode` | 只能是 `追读向`、`短剧口播` 或 `氛围短篇` |
| `engine` | 一个可重复产生下一章的主引擎，非空 |
| `relationship_debts` | 数组；没有欠账时写 `[]`。每项含非空 `who`、`owes`、`what` |

`STATE.data.changes` 为非空数组，每项含 CH 事件引用 `event_ref`，以及非空 `before`、`after`、`effective_node`、`story_time`。另外三项必须是数组，没有记录时写 `[]`，不能再把整段说明塞进一个字符串：

| 字段 | 每项必填 | 状态枚举 |
| --- | --- | --- |
| `knowledge` | `who`、`fact`、`status`、`event_ref` | `知道`、`怀疑`、`误信`、`未知` |
| `possessions` | `holder`、`fact`、`event_ref` | 无 |
| `foreshadowing` | `fact`、`status`、`event_ref` | `已埋`、`推进`、`已回收`、`未回收` |

`event_ref` 必须指向已保存章节的实际事件。阅读模式、主引擎、欠账和这三项数组在保存有实际内容的工作稿时检查；字段缺失或枚举错误不能存成新版本。全空骨架仍可保存为草稿，但不能采用。字段规则生效前已经保存、且从未采用的旧快照只作警告，不能改写。一旦采用，该版本按完整字段检查。工具仍不判断“知道”和正文是否语义矛盾，语义由内容审核核对。

其他类型的 `data` 为包含实际内容的对象，由对应技能提供。只有栏目、空字符串或空数组的骨架不是完整内容。镜头文字和提示词正文不能包含 `undefined`、`null`、`同上`、`见上` 或待填占位。`PROMPT` 至少要有一条可复制的 `image_prompt`、`video_prompt` 或 `prompt`，并写明 `negative_prompt`；没有额外排除时写“无额外项”。未再采用的旧快照只警告，当前工作稿和当前采用版按错误处理。工具不推断小说好坏、不自动生成缺失设定，也不把自由文本中的文学矛盾判定为已检查。

### 关键帧与参考职责（沿用 PROMPT）

需要独立生成或管理版本的关键帧沿用 PROMPT，单张图片的可复制正文放 `image_prompt`，`data.shot` 指向确切 SHOT 版本。`frame_purpose`、`design_id`、前后状态等是可选制作说明，设计编号不能冒充已生成视频的实测帧号。未生成图片只属于待素材计划，不能登记为已存在 MEDIA；旧 PROMPT 不需要增加字段。

一次生成包含多个剪辑镜头时，`data.shot` 仍指向首个／主镜的确切版本；可选 `data.shot_refs` 按播放顺序列出本任务涉及的全部 SHOT 直接引用，并包含主镜。各镜动作、时间安排和素材取用关系在正文或附件展开，不能只列引用后省略分镜；不要把生成任务总时长再加到各 SHOT 播放时长上。同集与跨集依赖沿用现有引用闭包和按集导出范围检查，跨出所选剧集的组合提示词可能被排除并提示拆分或扩大范围；本约定不新增类型、必填字段或专属验证器。

实际取得的参考素材可在下游 PROMPT 中用可选 `reference_bindings` 说明职责：

```json
{
  "shot": {"asset_id": "IP003-SHOT-001", "version": "1.0.0"},
  "video_prompt": "石桥上，执剑者保持右手持剑，沿对手左侧格挡后收回剑锋。",
  "negative_prompt": "避免兵器换手或重复出现。",
  "reference_bindings": [
    {
      "media": {"asset_id": "IP003-MEDIA-001", "version": "1.0.0"},
      "file_path": "素材/接触姿态.png",
      "expected_usage_id": "KF-A-K1.contact",
      "role": "动作与接触关系参考",
      "allowed": ["右手持剑", "剑刃接触位置"],
      "forbidden": ["沿用图片中的二维平涂画风"]
    }
  ]
}
```

以上 ID 仅示范结构，使用时必须替换为实际存在、已保存且满足采用条件的版本。`media` 单独作为正式引用；`file_path` 相对所引 MEDIA 的资产目录。声明 `reference_bindings` 时，工具检查它是数组（空数组可用），每项含 MEDIA 精确版本引用和安全相对文件路径；读取所引版本的冻结快照，对照该版 `data.files`、快照文件清单和实际普通文件，并复用快照哈希校验。路径仅将正反斜线统一为 `/`，其余按冻结清单实际拼写匹配，不从工作稿或最新采用版猜选图片。职责与路径不能塞入 `{asset_id, version}` 引用对象。

`MEDIA.data.files[].usage_id` 与绑定项的 `expected_usage_id` 是可选用途标识，声明时必须为非空字符串，保留原值并精确比较。图像实际查看后可登记角色视图或设计帧用途，例如 `CHAR-A.front`、`KF-A-K1.contact`；同用途允许多个候选。绑定声明 `expected_usage_id` 后，所选文件缺少 `usage_id` 或值不同会报错；工具不根据文件名、`role` 或图片内容猜用途。上例要求所引 MEDIA 的该文件登记 `usage_id: "KF-A-K1.contact"`。

无 `reference_bindings` 的旧 PROMPT 无需补字段；有绑定但无 `expected_usage_id` 时仍做文件校验，警告用途匹配未启用。新规则沿用工作稿／当前采用版错误、旧非当前快照警告的结构兼容处理；重新采用或作为正式导出依赖时按正式检查。快照哈希损坏始终报错，不降级。警告随检查、保存、采用、漫改导出和续作包保留。文件和标识通过只证明登记对应，身份、姿态、参考职责及平台输入仍需实际查看核对。

制作顺序为 SHOT → 图片 PROMPT → 实际图片 MEDIA → 视频 PROMPT → 实际视频 MEDIA，下游引用上游；视频 PROMPT 仍直接关联所属 SHOT。SHOT 不反向引用由自身衍生的关键帧或视频，以免形成循环依赖。长篇序列设计、当次模型适配依据可作为所属 PROMPT 或其他适合资产的目录内附件，随该版本冻结；附件文件名和相对路径可写在制作说明中，不建立新资产类型、关键帧数据库或必填机器字段。

### 实际媒体 MEDIA

`MEDIA.data.files` 为文件清单，每项有相对本资产目录的 `path` 和分类 `kind`：

```json
{
  "files": [
    {"path": "素材/人物参考.png", "kind": "image"},
    {"path": "素材/对白.wav", "kind": "audio"}
  ]
}
```

`kind` 只允许 `image`、`video`、`audio`、`other`。采用时至少包含一个真实普通文件；路径不能越出资产目录，不能使用绝对路径、符号链接、目录联接、重复路径，不能将 `asset.json` 或 `_snapshot.json` 当媒体。声明了文件就必须存在；草稿允许空 `files`，不能据此采用。

文件随资产快照保存、校验并进入依赖交接包。旧 `file_path` 字符串或“已生成”状态文字不能证明媒体存在，旧媒体登记须实际补齐文件清单。文件存在与校验通过不证明画面、音频、编码或文件分类正确，仍需实际打开检查。本规范示例不表示这些参考文件已经生成。

需要用途匹配时，文件项可增加 `usage_id`，例如 `{"path":"素材/人物参考.png","kind":"image","usage_id":"CHAR-A.front"}`。用途改变或文件替换均保存新版本；不改写旧快照来消除绑定错误。

### 生成返修台账与剪辑附件（沿用 REPORT）

每集按需使用 REPORT 保存[生成与返修台账](../模板库/17_生成与返修台账模板.md)及[剪辑取用与转场交接](../模板库/18_剪辑取用与转场交接模板.md)。模板是人读记录，不增加机器台账 schema。任务编号、尝试编号及候选定位采用普通文本，不能命名为 `asset_id` 或伪装成正式引用。台账保留实际提交正文、设置与输入、候选文件、问题位置、修改因素、复查和采用理由；图片区域、素材时码、成片时码及设计节拍分开。

REPORT 的 `refs` 或 `data` 正式引用列出需随包的 SHOT、PROMPT 和采用 MEDIA 精确版本。一般附件里的编号不会自动形成依赖。未采用尝试以 `ID@version` 文本定位；需随包复查的失败正文及媒体复制为 REPORT 的证据附件并明确未通过或未检查，不为了台账采用失败 MEDIA。REPORT 位于依赖末端，MEDIA 不反向引用含自身候选结果的 REPORT。工作台账先保存草稿；已采用报告有新增记录时递增版本再保存，旧记录不覆盖。跨集记录拆成各集报告，以免按集导出时因范围外制作节点被整体排除。

剪辑附件另记素材入出点、成片位置、转场重叠、余量和唯一连续声轨。默认以秒数、恒速取用记录，有实测帧率才使用帧号；素材总长和区间注明规划或实测及依据。SHOT 仍保留不重叠规划，附件并列最终成片时间和差异，不倒填原规划。两段各6秒、重叠1秒的占屏时间为11秒；同一句连续对白只登记和取用一次。附件供人工剪辑交接，工具不执行叠化或自动判定动作、节拍与声画同步。

## 4. 快照、采用与复核处理

历史位置为 `.ip-system/snapshots/ID/version/`，包含原始文件及 `_snapshot.json` 哈希清单。登记项 `versions` 记录 `version`、`path`、`created_at`、`modified_at`、`manifest_sha256`。保存时可选修订依据 `--reason` 写入快照清单和操作日志的 `reason`；未填为“保存本轮工作稿快照”。工作稿变化不影响快照；同版本号不可再次保存，快照被改动会触发完整性错误。

`adopt` 对指定快照严格检查，其依赖版本必须曾正式采用。工具记录采用时间、依据、操作证据和当前指针，不回写冻结快照的语义标签。采用上游新版生成 `review_items`，列出受影响下游；内容与引用不会被自动改写。

复核提示沿依赖关系传播到间接下游，例如 WORLD→CH→EP→SC→SHOT→PROMPT。`review_items` 可包含 `via`：直接依赖时为空数组，间接依赖时记录途中 `ID@version` 字符串列表。提示仅说明影响路径，不自动改引用或关闭创作问题。

每项复核包含稳定 `review_item_id`，由下游ID/版本、上游ID/固定旧版/当前新版及有序 `via` 共同确定。确实核查后保留历史引用时，工具在 `review_dispositions` 登记 `decision: "keep-history"`、上述精确身份、`reason`、`evidence`、`method`、`reviewer`、实际 `recorded_at`。只有同一组合的提示会被处理；任一端版本或中间路径变化后重新出现。需要更新引用时实际保存、采用下游新版本，不用保留历史结论代替修改。

## 5. 内容审核证据

`record-review` 接收项目内的 JSON 审核输入，绑定已经保存的资产快照。审核者应在实际读取后填写，工具只保存证据，不自动创作审核结论。审核与复核输入使用 `method` 表示审查方式，审核使用 `result` 表示结论；不接受旧字段名 `reviewer_kind` 或 `conclusion`。

| 输入字段 | 要求 |
| --- | --- |
| `method` | `ai` 或 `human`；AI与人工分别记真实记录，不把共同参与写成未经发生的人工审核 |
| `reviewer` | 实际审核者名称，不留空或待填 |
| `scope` | 实际读过和核对的具体范围 |
| `coverage` | `full` 或 `partial`，省略默认 `partial` |
| `result` | `pass`、`revise` 或 `unverified` |
| `issues` | 问题数组；确无问题时显式 `[]` |
| `evidence` | 整体检查依据与实际观察，非空文本 |
| `reviewed_at` | 可选，真实发生且带时区的 ISO 时间；不提供时工具不代填审核时间 |

每个问题有唯一 `id`，`severity` 为 `blocker`、`revision` 或 `suggestion`，`status` 为 `open` 或 `resolved`，另有非空 `description`、`evidence`。只交修改稿、只应用修改但没有复查时仍为 `open`；只有实际复查通过才标 `resolved`。存在未解决的 `blocker` 或 `revision` 时不能声明 `pass`。

工具补入 `schema_version`、唯一 `review_id`、`project_id`、`asset_id`、`version`、`manifest_sha256` 和真实 `recorded_at`，保存为 `.ip-system/reviews/review_id/review.json`。项目 `content_reviews` 登记路径和记录校验，不能改原记录假装它审过新稿。

启用审核约束时必须满足：精确ID、版本和快照校验一致，`coverage: "full"`，`result: "pass"`，没有未解决的阻塞或应修订问题。同一快照后续若新增未通过审核，不能重用旧通过记录绕过；须完成新的完整复审。

`adopt --review` 绑定确切记录；`export --require-review` 对本次交接范围的章节执行审核检查。布局v2采用必须带 `--review`，导出默认且强制执行播放章节完整审核。布局v1旧命令仍可不带审核参数运行，但明确提示未绑定审核；兼容使用不构成内容已通过的证据。

## 6. 漫改交接范围与小说续作

漫改 `export` 至少需要已采用 CH、EP、SC、SHOT；默认导出整个项目，也可互斥地使用 `--episodes` 或 `--chapters` 选择范围。参数为完整资产ID的逗号分隔列表，使用所选当前采用成果及完整依赖闭包；依赖可固定到曾采用历史版，从未采用版不能入包。

按章节选择会找到使用这些章节的剧集，并按完整剧集交接；多章合一集时也会包含该集实际需要的其他章节。报告或状态引用的范围外章节可能作为证据入包，不因此增加播放镜头。跨出所选剧集制作节点的附属交接资产会被列为警告，需拆分该资产或扩大范围。

输出 `handoff.json`、`交接说明.md`、`来源与版本清单.json`、`内容审核记录.json` 和完整 `assets/` 快照。v2目标必须在项目 `deliveries/handoff/` 下；v1目标仍在 `07_发布资产/` 下，不能与工作目录相互包含，不覆盖已有目录。`--require-review` 要求实际播放树使用的每个章节版本具有精确快照的最新完整通过记录，不把范围外证据章节自动算成已审播放内容。

`交接说明.md` 的镜头补充内容、完整 PROMPT 和随包附件链接都来自同一采用快照。附件清单由快照文件清单产生，排除已单独组织的资产元数据和 CH 七文件；路径按片段编码，支持空格、`#`、括号等文件名。后续修改工作目录中的说明不改变已导出的附件。依赖入包不代表播放范围扩大，也不代表参考图或视频已通过人工观看验收。

完整性检查覆盖每个 CH、EP、SC 资产 ID：CH 必须有对应 EP，EP 必须有 SC，SC 必须有 SHOT。全新资产 ID 没有下游时报告缺项；同一资产 ID 的新版尚未桥接时，可以保留其历史曾采用版的完整制作链并提示复核，不能宣称旧分镜已经使用新版。已保存未采用稿不入包。相同播放层级编号及时间冲突按导出检查结果处理。

`handoff.json` 顶层包含 `schema_version`、`project_id`、`project_name`、`exported_at`、`scope`、`selection`、`require_review`、`content_reviews`、`warnings`、`assets`、`content`、`review_items` 和 `playback`。`selection` 为 `{type: "all"|"EP"|"CH", asset_ids: [...]}`；`content_reviews` 列审核记录ID，完整记录在同包 `内容审核记录.json`。`content` 是资产元数据，正文等附属文件在 `assets/ID/version/` 中。

`assets` 清单含资产 ID、版本、类型、标题、来源、语义采用状态 `semantic_adoption_status`、当前采用版 `current_adopted_version`、快照校验 `manifest_sha256`、包内路径 `path` 和 `refs`。来源清单另含该批版本的真实 `adoption_history`。

`playback` 表达实际播放覆盖，与完整资产依赖清单分开：

```json
{
  "chapters": [{"asset_id": "IP003-CH-001", "version": "1.0.0"}],
  "episodes": [{"asset_id": "IP003-EP-001", "version": "1.0.0"}],
  "scenes": [{"asset_id": "IP003-SC-001", "version": "1.0.0"}],
  "shots": [{"asset_id": "IP003-SHOT-001", "version": "1.0.0"}],
  "uncovered_adopted_versions": []
}
```

未被当前镜头使用的同 ID 新采用版列在 `uncovered_adopted_versions`，条目包含 `asset_id`、`version`、`type`、`reason`。此时保留完整旧版制作链并警告，不能把“资产已入包”写成“新版已完成漫改”。

`status` 只读返回 `assets`、`adopted`、`drafts`、`pending`、`production_notes`、`review_items`、`resolved_reviews` 和 `errors` 等状态。资产行区分 `work_version`、`adopted_version`、`unsaved_changes`、历史版本数量；待办由未保存、未采用、章节缺审核、上游待复核及未完成事务生成。`production_notes` 摘录已采用 REPORT 的制作状态、下一动作等内容；`pending` 为空不代表报告中预演、媒体或其他创作任务完成。状态查看不代替完整结构检查，也不自动决定下一章剧情。

`resume` 不要求分集或分镜，复制所有已采用资产及其历史依赖至v2的 `deliveries/resume/` 下新的续作目录；v1使用 `00_项目管理/`。输出 `续作说明.md`、`续作信息.json` 和 `assets/`；工作稿只列状态和问题，不混入正文基准。`续作信息.json` 含资产版本和哈希、`states`、`pending`、`production_notes`、`working_errors`、`warnings`、`review_items`、`review_dispositions`、`reading_list`、`content_reviews`。所打包快照的检查警告去重后写入 `warnings`、命令返回和中文说明，不能在续作时丢掉旧绑定未启用用途匹配等提示。读取清单按设定、剧情、人物、状态和章节等组织，章节列七文件路径。真实创作目标与下一章安排仍从章纲、报告或用户当前任务读取。

## 7. 写入保证

同项目写操作使用进程锁、临时目录、完整性校验和提交日志。只读检查报告待恢复事务；后续写操作对中断事务验证并继续提交。读取项目时记录校验值，提交前发现外部改动会拒绝覆盖。

可确认原进程已退出的本机锁，通过按旧锁 token 唯一登记的持久恢复声明协调清理；活动锁或无法识别的锁拒绝写入。若负责清理旧锁的恢复进程再次中断，声明保留并报错，需要核对现场，不自动猜测解除。无法验证的证据保留，不强行清理或覆盖历史。

## 8. 布局、迁移与资产生命周期

布局v2只改变项目清单的布局版本、工作资产路径及非资产文件的用途分区；13类资产、内容schema1、ID、版本引用、章节七文件和冻结快照协议不变。迁移保留历史快照、哈希与历史采用记录；旧导出和续作记录的路径通过工具保存的迁移映射解析，不重写历史记录。

停用与恢复仅处理v2未曾采用、未被已采用下游引用的候选，只维护项目层的资产生命周期，不向 `source_kind`、`adoption_status` 添加新枚举，也不删除工作文件或快照。登记项的 `lifecycle` 为 `active` 或 `retired`，省略按active；`lifecycle_history` 由工具追加真实前后状态、理由、时间和operation_id。停用资产保留文件、版本与审核，status仍可查询，但退出行动待办；恢复后仍需保存、审核并采用。具体约束和命令见[接口规范](接口规范.md)及[重构实施说明](重构实施说明.md)。
